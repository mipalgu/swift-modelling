# Format-Specific Constraints

## XMI (XML Metadata Interchange)

### Strengths
- Standardised by the OMG and written by EMF-based tools
- Classes are named by namespace prefix (`pm:Organisation`)
- Containment is the nesting of XML elements

### Constraints
- Verbose and awkward to consume in a browser
- References are fragment paths (`#//@members.0`) that depend on the
  position of the target object
- A textual `diff` of two XMI files mixes layout with content

### Reference Example
```xml
<tasks id="TASK-004" title="Implement customer data API" status="NOT_STARTED">
  <assignee href="#//@members.1"/>
  <dependencies href="#//@projects.0/@tasks.2"/>
</tasks>
```

## JSON (as written by swift-ecore convert)

### Strengths
- Native to web browsers and REST interfaces
- Every object names its class in `eClass`, so no information is lost
- Keys are sorted, so files are stable under version control

### Constraints
- JSON itself has no types: the metamodel says what a key means
- References are `{"$ref": "//@members.1"}` objects with the same
  fragment paths as XMI
- Numbers lose their spelling (`40.0` is written as `40`)

### Reference Example
```json
{
  "assignee" : { "$ref" : "//@members.1" },
  "eClass" : "http://www.example.org/projectmanagement/1.0#//Task",
  "id" : "TASK-004",
  "status" : "NOT_STARTED",
  "title" : "Implement customer data API"
}
```

## Swift (generated value types)

### Strengths
- The compiler checks every access
- Enumerations become Swift enums with the literal names as raw values
- `Codable` reads and writes the JSON format directly

### Constraints
- Types must be regenerated when the metamodel changes
- References stay `ModelReference` values that the app resolves
- A struct cannot contain itself, so recursive containment needs care

## Translation Matrix

| Feature        | XMI                 | JSON                 | Swift               |
|----------------|---------------------|----------------------|---------------------|
| Class          | `pm:Class` element  | `eClass` URI         | struct              |
| Containment    | nested element      | nested object        | nested array        |
| Reference      | `href` fragment     | `$ref` fragment      | `ModelReference`    |
| Enumeration    | literal name        | literal name         | enum (raw value)    |
| Dates          | ISO 8601 text       | ISO 8601 text        | `String`            |
| Identity       | `id` attribute      | `id` key             | `id` property       |

Dates are `EString` attributes holding ISO 8601 text, so that every
format keeps them exactly as written.

## Consequences for the Integration

1. Use one metamodel for every format and validate each file against it.
2. Convert formats with `swift-ecore convert -m ProjectManagement.ecore`,
   which keeps classes, references and enumeration literals.
3. Use a transformation only when the *structure* must change, such as a
   compact view for web clients.
4. Compare models, not files: `swift-ecore compare` matches objects by
   their identifiers, whatever the format.
